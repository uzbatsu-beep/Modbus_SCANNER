# Справочник по протоколу Modbus

[English version](MODBUS.md)

Здесь описано именно то, что реализовано в сканере. Общая архитектура — в
[ARCHITECTURE.ru.md](ARCHITECTURE.ru.md).

## 1. Модель данных и адресация

Четыре классические таблицы по 65536 элементов:

| Таблица | Доступ | Функции |
|---------|--------|---------|
| Coils (0XXXX) | чтение/запись | 01, 05, 15 |
| Discrete inputs (1XXXX) | только чтение | 02 |
| Holding registers (4XXXX) | чтение/запись | 03, 06, 10, 16, 17 (hex: 03, 06, 0x10, 0x16, 0x17) |
| Input registers (3XXXX) | только чтение | 04 |

**Важно:** нумерация 1-based (40001 и т.п.) — это лишь *обозначение в документации*.
В PDU всегда передаётся **0-based** адрес (`u16`, 0…65535). В UI используются
0-based адреса; если в руководстве устройства указано 40001, вычтите 1.

Ограничения на количество элементов в запросе (спецификация):

| Функция | Максимум |
|---------|----------|
| 01 / 02 (биты) | 2000 |
| 03 / 04 (регистры) | 125 |
| 0F (запись coil) | 1968 |
| 10 (запись регистров) | 123 |

## 2. PDU

```
PDU = [код функции (1 байт)] [данные (0…252 байта)]
```

- Обычный ответ: тот же код функции + данные.
- Ответ-исключение: код функции **| 0x80** + один байт кода исключения.

## 3. Варианты ADU

### RTU (последовательный порт, бинарный)

```
[slave id (1)][PDU (1…253)][CRC-16 мл. (1)][CRC-16 ст. (1)]
```

Максимальный размер ADU — 256 байт. CRC-16/Modbus: полином `0xA001`
(отражённый `0x8005`), начальное значение `0xFFFF`, финального XOR нет;
передаётся **младший байт первым**. Slave id `0` = broadcast (ответа нет,
поэтому сканирование адреса 0 всегда даёт «нет ответа»). Рабочие адреса: 1–247;
248–255 зарезервированы.

Фрейминг основан на паузе: границей кадров служит интервал тишины **≥3.5 времени
символа (t3.5)**. При скоростях ≥19200 специя фиксирует t3.5 = 1,75 мс.
`SerialTransport` дополнительно использует детектор тишины 5 мс перед завершением
RTU-кадра и межкадровую паузу перед передачей.

### ASCII (последовательный порт, hex-текст)

```
':' [slave id hex (2)][PDU hex (…)] [LRC hex (2)] CR LF
```

Каждый байт — два символа hex в верхнем регистре. LRC = дополнительный код до 2
от суммы байтов полезной нагрузки (slave id + PDU), вычисляется как
`wrapping_neg()` от `u8`-суммы. При декодировании сканер допускает строчные hex.
Конец кадра — CRLF; на практике также используется правило 1-й паузы тишины.

### TCP (MBAP)

```
[transaction id (2)][protocol id (2)=0][length (2)][unit id (1)][PDU]
```

Все поля big-endian. `length` — число байтов *после* этого поля (unit id + PDU),
то есть для запроса чтения одного регистра `length = 1 + 5 = 6`.
Сканер генерирует возрастающий transaction id на каждый запрос и **проверяет,
что ответ его возвращает** (несовпадение — ошибка `TransactionIdMismatch`, а не
запись устройства). Protocol id должен быть 0; стандартный порт — 502 (часто
503, 1502, 802). Кроме обычного MBAP сканер умеет отправлять сырой RTU-кадр
поверх TCP (`tcp_framing = "rtu"`, часто у последовательных шлюзов) — в этом
режиме MBAP-заголовка нет.
Unit id нужен для маршрутизации через шлюзы; напрямую подключённые TCP-устройства
обычно отвечают на unit 1, 0 или 255.

### UDP

Не входит в оригинальную спецификацию, но часто применяется. В полях встречаются
два варианта полезной нагрузки:

1. **MBAP + PDU** (чаще всего, как в TCP);
2. **ADU в стиле RTU** (slave id + PDU + CRC).

`UdpTransport` считает одну датаграмму одним ADU. Отсутствие датаграммы за время
таймаута — нормальный отрицательный результат. По умолчанию сканер формирует для
UDP ADU в стиле RTU; при `udp_mbap = true` используется MBAP с той же проверкой
transaction id, что и в TCP.

## 4. Коды функций, используемые сканером

| Код | Название | Направление | Роль в сканере |
|-----|----------|-------------|----------------|
| 0x01 | Read Coils | чтение | зонд + карта регистров |
| 0x02 | Read Discrete Inputs | чтение | зонд + карта регистров |
| 0x03 | Read Holding Registers | чтение | зонд по умолчанию + карта регистров |
| 0x04 | Read Input Registers | чтение | зонд + карта регистров |
| 0x05 | Write Single Coil | запись | ручная консоль |
| 0x06 | Write Single Register | запись | ручная консоль |
| 0x0F | Write Multiple Coils | запись | ручная консоль |
| 0x10 | Write Multiple Registers | запись | ручная консоль |
| 0x16 | Mask Write Register | запись | только в `FunctionCode`, сборщик/парсер не реализованы |
| 0x17 | Read/Write Multiple Registers | чтение/запись | только в `FunctionCode`, сборщик/парсер не реализованы |
| 0x2B | Read Device Identification (MEI 0x0E) | чтение | базовая идентификация найденных устройств (P2-05) |

Диагностические коды (0x07, 0x08, 0x0B, 0x0C) и идентификация устройства 0x2B
по спецификации доступны только по последовательному порту и **пока не выведены**
в UI (см. ROADMAP).

## 4a. Modbus Security / TLS (E-05)

Официальная спецификация Modbus Security инкапсулирует MBAP-кадр в TLS на порту
**802**. `ScanParams.tls = { client_cert?, client_key? }` включает его; внутри
туннеля остаются те же MBAP-фрейминг и проверка transaction id. Сертификат сервера
проверяется через набор корневых CA webpki; пара PEM client cert/key включает
взаимную аутентификацию. Самоподписанные устройства требуют доверенного CA.
`tcp_framing = "rtu"` нужен только если шлюз ожидает сырой RTU-кадр (для Modbus
Security обычно нет).

## 4b. Идентификация устройства (FC43 / MEI 0x0E, P2-05)

PDU запроса (категория 1 — базовая идентификация):

```
[0x2B][0x0E][0x01][0x00]
      MEI  код запроса id объекта (0 = первый объект)
```

Данные ответа (после кода функции):

```
[MEI=0x0E][код запроса][уровень соответствия][есть продолжение][след. id][count]
  дальше `count` объектов:
  [id объекта (1)][длина (1)][значение (длина байт, текст)]
```

Стандартные базовые объекты: `0` VendorName, `1` ProductCode, `2` MajorMinorRevision.
Категория 2 (regular) добавляет VendorUrl, ProductName, ModelName, UserAppName.
Уровень соответствия: 0x01 — только базовый, 0x02 — regular, 0x03 — extended.
Сканер запрашивает базовую идентификацию один раз для каждого найденного
устройства (best effort): исключение или некорректный ответ просто оставляет
`device_identification` пустым.

## 5. Декодирование ответов

**Биты (FC 01/02):** первый байт нагрузки — количество байт, дальше упакованные
биты, младший бит первым:

```
[count=2][биты 7..0 для 0..7][биты 7..0 для 8..15]...
```

**Регистры (FC 03/04/17):** первый байт — количество байт (чётное), дальше
значения `u16` в big endian.

UI показывает регистры в hex, десятичном и 16-битном двоичном виде.

### Строгая проверка ответов (PR #5)

Обнаружение устройств, адаптивный поиск регистров, ручное чтение и мониторинг
используют единый валидатор полезной нагрузки:

- FC01/FC02: запрошено 1–2000 бит; поле `byte count` должно строго
  равняться `ceil(quantity/8)`, фактическая длина — соответствовать ему.
  Неиспользуемые биты последнего байта допускаются.
- FC03/FC04: запрошено 1–125 регистров; количество байт строго
  `2 × quantity`, чётное и не более 250; обрезанные и лишние байты запрещены.
- PDU не длиннее 253 байт. Ответ-исключение содержит **ровно 2 байта**,
  исходный FC запроса с битом 0x80 и допустимый код исключения.
  Исключение другого FC не доказывает наличие устройства.
- Для TCP/MBAP, включая ручной режим, проверяются Transaction ID,
  Protocol ID=0, фактическая длина и Unit ID.
- FC43: количество и длина объектов должны точно соответствовать пакету.

Повреждённый ответ выдаёт ошибку, **не** превращается в «успешное пустое
чтение», не создаёт фиктивных регистров и не увеличивает счётчик успехов.
При ошибке структуры PDU адаптивный обход не дробит диапазон дальше.

Проверка структуры протокола не заменяет корректную интерпретацию
типов данных, масштабирования и технологических величин.

## 5b. Многорегистровые значения и byte order (P3-01)

Два последовательных регистра `w0 w1` (каждый передаётся big-endian) могут
образовывать 32-битное значение в четырёх раскладках:

| Название | Сборка |
|----------|--------|
| ABCD | `(w0 << 16) \\| w1` — стандартный big-endian |
| BADC | байты переставлены внутри каждого слова |
| CDAB | слова переставлены |
| DCBA | слова и байты переставлены |

Инспектор показывает все интерпретации и помечает правдоподобные float32 как
**гипотезы** (например «возможно float32 (ABCD)»), никогда как факт. Именованные
теги добавляют масштабирование `(raw × multiplier ÷ divider) + offset` и единицу.

## 6. Коды исключений

`ModbusError::from_exception` отображает все стандартные коды:

| Код | Значение |
|-----|----------|
| 0x01 | Недопустимая функция |
| 0x02 | Недопустимый адрес данных |
| 0x03 | Недопустимое значение данных |
| 0x04 | Ошибка устройства |
| 0x05 | Подтверждение (Acknowledge) |
| 0x06 | Устройство занято |
| 0x07 | Отрицательное подтверждение |
| 0x08 | Ошибка чётности памяти |
| 0x0A | Маршрут шлюза недоступен |
| 0x0B | Целевое устройство шлюза не отвечает |

Ответ-исключение всё равно доказывает, что устройство живо; сканер помечает такой
зонд как «устройство найдено» с пометкой `exception` в UI.

## 7. Проверки движка

Для каждого ответа по порядку:

1. контрольная сумма (CRC для RTU/UDP, LRC для ASCII);
2. совпадение unit id с запросом (TCP: байт 6 MBAP);
3. совпадение кода функции (или корректное `fc | 0x80`);
4. protocol id MBAP == 0 и правдоподобная длина (TCP);
5. структура нагрузки и согласованность байтовых счётчиков.

При несовпадении ошибка уходит в транспортный слой, запись об устройстве не
создаётся.

### Ручная запись и стабильность RTU-over-TCP (PR #6)

- Для FC05/FC06 подтверждение должно **точно повторять** адрес и значение
  записанного параметра; для FC10 — начальный адрес и количество регистров.
  Совпадения одного FC недостаточно для успешного подтверждения записи.
- Пустые и слишком длинные Raw Frame запрещены до отправки. Получение
  Raw-ответа не является проверенным подтверждением исполнения записи.
- Команды записи и произвольные Raw Frame **никогда не повторяются автоматически**,
  даже после потери ответа или таймаута. Повторы доступны только для чтения.
- Таймаут записи — **неизвестный результат исполнения**, а не доказательство,
  что устройство не получило команду. Перед новой записью необходимо прочитать
  фактическое состояние. Это не аварийный останов и не гарантия exactly-once.
- RTU-over-TCP ждёт первого байта до истечения общего таймаута операции,
  собирает полный кадр по ожидаемой длине для основных FC и FC43, ограничивает
  RTU ADU 256 байтами. TLS handshake ограничен таймаутом подключения.
- Буфер чтения RTU ограничен 256 байтами, ASCII — 513 байтами; переполнение
  и некорректные кадры приводят к ошибке без неограниченного роста памяти.

## 7b. Разрешения OT и Quiet Mode (PR #7)

Пустой `ip_allowlist` запрещает TCP/UDP-сканирование до открытия сокета;
перед началом необходимо указать разрешённые IP/CIDR.
Исключения имеют приоритет. Все адреса диапазона, кроме явно исключённых,
должны находиться в разрешённой зоне. Для одиночных устройств и
адаптивного сканирования регистров действует тот же контроль.
DNS-имена запрещены из-за возможности подмены разрешения IP.

Quiet Mode реализует **общий для сканера** интервал не менее 500 мс
между началами физических транзакций. Ограничитель один для всех
параллельных IP-потоков; учитываются повторы, FC43 и чтения карты.
Уже отправленный запрос отозвать нельзя. Ограничение не гарантирует
детерминированную сетевую задержку шлюзов и не заменяет OT-процедуры.

## 8. Контрольные кадры (тест-векторы)

Чтение holding-регистров, unit 1, адрес 0, количество 10:

```
PDU: 03 00 00 00 0A
RTU: 01 03 00 00 00 0A C5 CD
ASCII: :01030000000AF2\r\n
TCP MBAP: 00 01 00 00 00 06 01 03 00 00 00 0A
```

Эти векторы покрыты юнит-тестами в `rtu.rs`, `ascii.rs` и `frame.rs`.
