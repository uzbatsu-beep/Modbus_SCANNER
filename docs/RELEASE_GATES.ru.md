# Контроль GitHub и согласование релиза (PR #9)

[English version](RELEASE_GATES.md) · [Windows QA](WINDOWS_QA.md) · [Стендовая приёмка](FIELD_VALIDATION_v1.0.1.md)

## Что включается автоматически, а что требует действий в GitHub

Файлы `.github/rulesets/*.json` — **шаблоны для импорта**, а не действующие
ограничения GitHub. Их необходимо импортировать и активировать в Settings.
Кроме того, обязательных утверждающих для Environment нельзя назначить
из YAML. **PR #9 не считается полностью внедрённым, пока эти настройки
не проверены на GitHub.** Preflight запрещает официальный релиз, если
активные Rulesets отсутствуют; публикация блокируется без секрета окружения.

## 1. Защита main

1. Перейдите в **Settings → Rules → Rulesets → New ruleset → Import a ruleset**
   и импортируйте `.github/rulesets/main.json`. Установите **Active**.
2. Убедитесь, что ограничена default branch `main`, нет обходных ролей
   (bypass), запрещены force-push и удаление. Для слияния требуется PR,
   одно **независимое** одобрение, сброс review при изменении кода,
   одобрение последнего push и закрытие обсуждений.
3. Включите проверку актуальности ветки и **все пять обязательных checks**:
   - `Governance (release gate tests)`
   - `Frontend (typecheck + build)`
   - `Backend (cargo check + tests) (windows-latest)`
   - `Backend (cargo check + tests) (ubuntu-latest)`
   - `Backend (cargo check + tests) (macos-latest)`
4. Пригласите **второго доверенного участника с правом write** для review
   изменений владельца. Автор PR не может одобрить собственные изменения.
   При единственном CODEOWNER включение обязательного CODEOWNER review
   может заблокировать все PR автора — поэтому в шаблоне требуется
   независимый review, но не обязательное одобрение CODEOWNER.

Импортируйте `.github/rulesets/release-tags.json` и активируйте защиту
`refs/tags/v*` от удаления и перезаписи. Создание нового тега разрешено,
так как его создаёт защищённый процесс Release после проверок.
**Сам push тега больше не запускает выпуск**.

Проверьте, что `main` отмечена как protected, оба Ruleset имеют статус
**Active**, прямой push в `main` запрещён, а незавершённый PR нельзя слить.
Не проверяйте это опасными force-push/delete операциями.

## 2. Независимое утверждение публикации

В **Settings → Environments → New environment** создайте
`production-release` и настройте:

- **Required reviewers** — доверенный пользователь, отличный от автора
  запуска Release; включите **Prevent self-review**.
- **Deployment branches** — только `main`.
- Environment secret **`OT_RELEASE_APPROVAL_GATE`** — случайное непустое
  значение, созданное в интерфейсе GitHub (не хранить в репозитории).
- Пробный запуск без одобрения должен остановиться в ожидании review.

Наличие секрета доказывает лишь выполнение настройки: само по себе оно
**не подтверждает независимое одобрение**. Его обеспечивает GitHub Environment.

## 3. Условия официального выпуска

До Release нужно:

1. Получить одобренный и слитый PR. Release запускается **только на main**.
2. Убедиться в успешном CI для **точного SHA main**, все пять проверок.
   CI ветки PR для публикации не подходит.
3. Убедиться в успешном Windows QA для **того же SHA main** и наличии
   действительного EXE/MSI-артефакта. QA запускается автоматически после
   push в `main` либо вручную через Actions.
4. Проверить физический изолированный стенд Modbus RTU/ASCII/TCP.
   Задокументировать результаты в **GitHub Issue** этого репозитория:
   SHA, оборудование/прошивка, параметры связи, методика, наблюдения,
   критерии PASS/FAIL, дату, одобрившего инженера и подтверждения.
   Без изолированного стенда не проводить активную запись в живом OT-процессе.
5. Проверить совпадение тега `vX.Y.Z` с версиями npm/Cargo/Tauri и
   отсутствие уже опубликованного тега/релиза.

В **Actions → Release (manual, protected) → Run workflow** выбрать `main`
и заполнить `tag`, `qa_run_id`, `bench_passed=true`, URL Issue.

Preflight проверяет SHA, Rulesets, пять CI-заданий, QA, версии и
существующие теги. Ссылка на стенд и отметка `bench_passed` —
**подтверждение инженера**, а не автоматический вывод о безопасности.
Сборка создаёт EXE/MSI, SHA256SUMS и BUILD-INFO.

Перед публикацией GitHub запрашивает approval для `production-release`.
После одобрения workflow повторно проверяет условия, наличие секрета
и создаёт релиз только для новой версии.

## 4. Если публикация заблокирована

- **Нет Ruleset или независимого reviewer:** импортировать правила и
  пригласить проверяющего.
- **QA SHA не равен main:** выполнить QA на текущем main, не переиспользовать
  артефакт чужого коммита.
- **Нет протокола стенда:** оставить пакет в QA, не выпускать официальный релиз.
- **Environment не настроен:** создать обязательный review и секрет.
- **Тег существует:** не перезаписывать; выпустить новую версию через PR.

## 5. Ограничения

Владелец репозитория при наличии прав администратора может изменить
настройки GitHub; поэтому важны процедура согласования и независимый
участник. Это не является сертификацией IEC 62443 и не заменяет
реальных испытаний устройств, шлюзов и линий RS-485.
