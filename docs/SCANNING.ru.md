# Сканирование

[English version](SCANNING.md)

## Цели сканирования

### 1. Последовательная шина (`unit_id_range`)

Один COM-порт, unit id от `from` до `to` (0–247). Для каждого id движок отправляет
все настроенные зондирующие FC (по умолчанию 03, 04, 01, 02). Один
`SerialTransport` открывается лениво и используется весь цикл — это сохраняет
арбитраж шины и межкадровую паузу t3.5.

Типичное применение:
- известная скорость — укажите её явно, например 9600 8N1;
- неизвестная скорость — повторите сканирование для каждой распространённой
  скорости (1200…115200), пресеты по скорости — в ROADMAP;
- неизвестная чётность — пробуйте 8N1, затем 8E1, затем 8O1.

Unit id 0 — broadcast: устройства не отвечают, не включайте его в диапазон без
особой цели проверить поведение broadcast.

### 2. Диапазон IP (`ip_range`)

Диапазон IPv4 (`from`–`to`) или CIDR (`from = "192.168.1.0/24"`, `to` пусто).
Диапазон ограничен 65536 адресами. Порт — 502 по умолчанию, но в полевых
устройствах часто 503/1502/802.

Для каждого IP сканер зондирует unit id **1 и 255** (типичные id прямого TCP и
транзита через шлюз). Modbus TCP-шлюзы маршрутизируют на последовательные
устройства по unit id; для id 2–247 используйте сканирование одного устройства.

TCP — запрос с MBAP-кадром; UDP — ADU в стиле RTU в одной датаграмме (нет ответа
= нет устройства). `TcpTransport` открывает новое соединение на каждый зонд —
это упрощает движок и устойчиво к устройствам, агрессивно закрывающим сокеты.

### 3. Одно устройство (`single_device`)

Одна конечная точка + явный unit id и `register_plan` — список диапазонов для
чтения. Для каждого найденного устройства заполняется карта `registers`.

## Параметры сканирования

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `timeout_ms` | 800 | Таймаут ответа на запрос (мс) |
| `request_gap_ms` | 20 | Пауза между запросами (мс) |
| `retries` | 1 | Повторы перед «нет ответа» |
| `probe_functions` | `[3, 4, 1, 2]` | FC для проверки наличия устройства |
| `stop_on_first` | false | Остановиться после первого найденного |
| `register_plan` | `[]` | Диапазоны для чтения на каждом устройстве |
| `ip_concurrency` | 32 | Запланированный лимит параллельных зондов IP |

**Примечание о реализации:** `timeout_ms`, `request_gap_ms`, `retries` и
`ip_concurrency` сейчас имеют фиксированные действующие значения в движке
(800 мс, без паузы, 1 повтор, последовательно). Они уже выведены в UI и в
IPC-контракте; подключение — в [ROADMAP.md](ROADMAP.md).

## Рекомендации по таймингам

| Сценарий | Таймаут | Пауза | Примечание |
|----------|---------|-------|------------|
| RTU @ 9600, 8N1 | 500–1000 мс | 20–50 мс | медленные устройства с пересчётом CRC |
| RTU @ 115200 | 200–500 мс | 5–10 мс | t3.5 ≈ 1,75 мс по спецификации |
| ASCII @ 9600 | 1000–2000 мс | 50 мс | текстовый фрейминг + CRLF |
| TCP в LAN | 200–500 мс | 0–10 мс | нет арбитража шины |
| UDP | 100–300 мс | 0 мс | без соединения: отсутствие ответа финально |
| RTU с 30+ устройствами | 300–600 мс | 20 мс | полный диапазон — минуты, планируйте время |

Правило: таймаут > (время ответа самого медленного устройства) × 1,5. Слишком
короткий таймаут даёт ложные пропуски, слишком длинный — медленное сканирование
247 адресов.

## Как работает обнаружение

1. Зонд: чтение 1 элемента с адреса 0 выбранным FC.
2. Любой корректный Modbus-ответ (данные **или** исключение) = «устройство найдено».
3. Ошибка CRC/LRC, несовпадение unit id, неожиданный FC или таймаут — нет.
4. Результаты накапливаются по ключу устройства:
   `rtu:COM3:1`, `tcp:192.168.1.5:502:1`, `udp:…`.
5. Найденные устройства сразу уходят в UI событием `scan:event`; таблица
   результатов обновляется вживую.

## Как читать результаты

- `OK rtt` — устройство ответило данными; hex-значения в панели деталей.
- `EXC 01/02/…` — устройство ответило исключением. Частый случай: адрес 0 не
  реализован → **Illegal data address (0x02)**. Устройство всё равно живо.
- `no_response` — таймаут после повторов. Возможно: неверный unit id, скорость,
  чётность или отсутствие устройства.
- `transport_error` — порт не открылся, соединение отклонено, битый кадр.
  Проверьте кабель/права на порт/файрвол.

## Практика полевых работ (по результатам исследования)

Полный список источников — в [RESEARCH.ru.md](RESEARCH.ru.md). Следующие практики
рекомендуются полевыми гайдами и будут реализованы в v0.2:

- **Неизвестные настройки шины:** сначала свип baud × framing, потом адреса.
  Приоритет: 9600 8N1 → 2400 8N1 → 19200 8N1 → варианты с чётностью (8E1).
  Останов — на первом сочетании с корректным CRC.
- **Дубли адресов:** два устройства с одним адресом отвечают одновременно →
  CRC-коллизии. CRC-ошибка не должна считаться найденным устройством.
  Рекомендация: подключать устройства по одному (point-to-point) и задавать адреса.
- **Только один master:** сканирование шины при работающем PLC даёт мусор —
  отключите master или работайте в «тихом окне».
- **Исключение 02 (Illegal Data Address)** — положительный сигнал: устройство
  живо, просто опрашиваемого адреса нет.
- **Открытый порт 502 — ещё не устройство:** нужен корректный Modbus-ответ.

## Безопасность

- При обнаружении сканер отправляет только **читающие** функции (01–04).
- Функции записи (05/06/0F/10) доступны только во вкладке Manual и требуют
  явного действия пользователя. См. [SECURITY.md](SECURITY.md).
- Не ждите ответа от unit id 0; broadcast-запись из Manual может повлиять на **все**
  устройства на последовательной шине.
- На шлюзах зондирование unit id 2–247 может дойти до реальных устройств.
  Соблюдайте осторожность.

## Прогресс и события

`scan:progress` несёт `{status, total, done, found, current, errors, elapsed_ms}`.
`scan:event` — смены статуса, найденные/обновлённые устройства и финальная сводка.
Полная схема — в [API.ru.md](API.ru.md).
