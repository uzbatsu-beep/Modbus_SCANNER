# Сканирование

[English version](SCANNING.md)

## Жизненный цикл и отмена запросов (PR #4)

При отмене оператором сканер проходит состояния
`Idle → Preparing → Running ↔ Paused → Stopping → Stopped`, при обычном
завершении — `Running → Finished`. Пока сканер находится в `Preparing`,
`Running`, `Paused` или `Stopping`, запуск второго задания запрещён
на уровне Rust, в том числе для CLI/API.

Команда `stop_scan` отправляет фиксируемый сигнал отмены **независимо от
очереди Pause/Resume**. Движок прерывает ожидание TCP/UDP и последовательного
I/O, ожидание свободного IP-слота и паузы между запросами, отменяет активные
задачи, очищает очередь регистровых чтений и закрывает последовательный
транспорт. Только после очистки публикуется `Stopped`.
`Paused` блокирует планирование новых задач, но не прерывает уже начатые
сетевые запросы.

**Важно:** это отмена программных транзакций, а не аппаратный аварийный
останов. Уже переданные устройству или буферизованные системой/адаптером RS-485
байты нельзя отозвать. Нельзя считать, что команда, отправленная до Stop,
не исполнилась на устройстве.

`stop_on_first` — отдельное условие прекращения обнаружения после первого
устройства. Предусмотренные планом чтения его регистров могут завершиться.

## Цели сканирования

### 1. Последовательная шина (`unit_id_range`)

Один COM-порт, unit id от `from` до `to` (0–247). Для каждого id движок отправляет
все настроенные зондирующие FC (по умолчанию 03, 04, 01, 02). Один
`SerialTransport` открывается лениво и используется весь цикл — это сохраняет
арбитраж шины и межкадровую паузу t3.5.

Используйте этот режим, когда настройки шины известны.

### 1b. Последовательная шина с неизвестными настройками (`serial_auto`, P2-01)

Включите «Авто-поиск настроек» в форме RTU/ASCII. Движок выполняет **двухфазный свип**:

1. **Фаза 1 — поиск настроек.** Для каждой чётности (8N1 → 8E1 → 8O1) и каждой
   скорости в порядке приоритета (9600 → 2400 → 19200 → 4800 → 38400 →
   57600 → 115200 → 1200) опрашиваются лишь несколько вероятных unit id:
   1, 2, 3, 4, 5, 10, 20, 100, 247. Кадр с корректной CRC/LRC — включая
   Modbus-исключение — считается ответом.
2. **Фаза 2 — полный скан.** Найденные скорость/чётность фиксируются, общий
   последовательный порт переоткрывается с ними, и сканируется весь диапазон
   unit ID. Другие сочетания больше не пробуются.

В UI можно ограничить набор скоростей и чётностей. При всех значениях по
умолчанию максимум — 8 × 3 × 9 = 216 коротких зондов; для свипа рекомендуется
таймаут ответа 200–300 мс.

Unit id 0 — broadcast: устройства не отвечают, не включайте его в диапазон без
особой цели проверить поведение broadcast.

### 2. Диапазон IP (`ip_range`)

Диапазон IPv4 (`from`–`to`) или CIDR (`from = "192.168.1.0/24"`, `to` пусто).
Диапазон ограничен 65536 адресами. Порт — 502 по умолчанию, но в полевых
устройствах часто 503/1502/802.

Для каждого IP сканер зондирует unit id **1 и 255** (типичные id прямого TCP и
транзита через шлюз). Modbus TCP-шлюзы маршрутизируют на последовательные
устройства по unit id; для id 2–247 используйте сканирование одного устройства.

TCP — запрос с MBAP-кадром; UDP — ADU в стиле RTU в одной датаграмме (нет ответа
= нет устройства). `TcpTransport` открывает новое соединение на каждый зонд —
это упрощает движок и устойчиво к устройствам, агрессивно закрывающим сокеты.

### 2b. Классы IP-целей (P2-04)

Для каждого `ip:port` в `ScanResults.ip_targets` ведётся классификация (видна
во вкладке «Результаты»):

| Класс | Смысл |
|-------|-------|
| `valid_modbus` | Хотя бы один корректный Modbus-кадр (данные или исключение) |
| `port_open_no_modbus` | TCP-соединение установлено, но по Modbus никто не ответил |
| `connection_refused` | Соединение TCP активно отклонено |
| `timeout` | Нет ответа за настроенный таймаут |
| `unreachable` | Хост/сеть недоступны |

Классы ранжированы и не понижаются при переборе unit id за одним IP.
Отказ/недоступность/таймаут не создают ложную запись устройства — цель
появляется только в таблице классификации. У UDP нет handshake, поэтому
положительный класс только `valid_modbus`, а тишина — `timeout`.

### 3. Одно устройство (`single_device`)

Одна конечная точка + явный unit id и `register_plan` — список диапазонов для
чтения. Для каждого найденного устройства заполняется карта `registers`.

### 3b. Адаптивная карта регистров (`register_scan`, P2-03)

Отдельный режим для случая «устройство отвечает, но документации на регистры нет».
Он читает диапазон адресов блоками и адаптируется к ошибкам:

| Режим | Поведение |
|-------|-----------|
| `Quick` | Блоки по `batch` (по умолчанию 100); неудачный блок делится на 1/5 один раз, затем границы уточняются по регистрам. Быстрее на непрерывных картах. |
| `Balanced` (по умолчанию) | 100 → 20 → 5 → одиночные регистры. Компромисс для смешанных карт. |
| `Deep` | Делит неудачные блоки до одиночных регистров. Находит изолированные регистры, но делает больше запросов. |

Общие правила:

- исключение **0x02** означает «адреса нет» → блок делится;
- исключение **0x01** (функция не поддерживается) или **0x03** → немедленный стоп;
- **таймауты не делятся** — повтор подблоков стоил бы полного таймаута каждый;
  три таймаута подряд прерывают сканирование;
- отвечающие адреса запоминаются, чтобы уточнение границ не перечитывало их;
- результаты попадают в запись устройства, даже если оно не было найдено
  предыдущим сканом.

Поле «Размер блока» в UI переопределяет значение режима; значение ограничивается
лимитом функции (125 регистров или 2000 coil).

## Параметры сканирования

| Параметр | По умолчанию | Смысл |
|----------|--------------|-------|
| `timeout_ms` | 800 | Таймаут ответа на запрос (мс) |
| `request_gap_ms` | 20 | Пауза между запросами (мс) |
| `retries` | 1 | Повторы перед «нет ответа» |
| `probe_functions` | `[3, 4, 1, 2]` | FC для проверки наличия устройства |
| `stop_on_first` | false | Остановиться после первого найденного |
| `register_plan` | `[]` | Диапазоны для чтения на каждом устройстве |
| `ip_concurrency` | 32 | Лимит параллельных зондов IP |
| `identify_devices` | true | Запрашивать FC43/MEI14 после ответа устройства |
| `tcp_framing` | `mbap` | Формат TCP: `mbap` или `rtu` (RTU поверх TCP) |
| `udp_mbap` | false | Использовать MBAP для UDP вместо ADU в стиле RTU |

**Примечание о реализации:** все четыре параметра действуют: в начале скана
движок вычисляет единый `EngineParams` (таймаут ограничен 50–10000 мс, ретраи
≤ 5, пауза ≤ 1000 мс, параллелизм IP 1–256). Последовательные зонды идут
строго один за другим; TCP/UDP-зонды выполняются в пуле с ограничением.
Пауза между запросами применяется после каждого элемента работы; пауза сканера
останавливает выдачу новых задач.

## Рекомендации по таймингам

| Сценарий | Таймаут | Пауза | Примечание |
|----------|---------|-------|------------|
| RTU @ 9600, 8N1 | 500–1000 мс | 20–50 мс | медленные устройства с пересчётом CRC |
| RTU @ 115200 | 200–500 мс | 5–10 мс | t3.5 ≈ 1,75 мс по спецификации |
| ASCII @ 9600 | 1000–2000 мс | 50 мс | текстовый фрейминг + CRLF |
| TCP в LAN | 200–500 мс | 0–10 мс | нет арбитража шины |
| UDP | 100–300 мс | 0 мс | без соединения: отсутствие ответа финально |
| RTU с 30+ устройствами | 300–600 мс | 20 мс | полный диапазон — минуты, планируйте время |

Правило: таймаут > (время ответа самого медленного устройства) × 1,5. Слишком
короткий таймаут даёт ложные пропуски, слишком длинный — медленное сканирование
247 адресов.

## Как работает обнаружение

1. Зонд: чтение 1 элемента с адреса 0 выбранным FC.
2. Любой корректный Modbus-ответ (данные **или** исключение) = «устройство найдено».
3. Ошибка CRC/LRC, несовпадение unit id, неожиданный FC или таймаут — нет.
4. Если включено `identify_devices`, отправляется один дополнительный запрос
   FC43/MEI14 (P2-05): VendorName / ProductCode / Revision. Это best-effort —
   исключение или некорректный ответ лишь оставляют поле пустым.
5. Результаты накапливаются по ключу устройства:
   `rtu:COM3:1`, `tcp:192.168.1.5:502:1`, `udp:…`.
6. Найденные устройства сразу уходят в UI событием `scan:event`; таблица
   результатов обновляется вживую.

## Как читать результаты

- `OK rtt` — устройство ответило данными; hex-значения в панели деталей.
- `EXC 01/02/…` — устройство ответило исключением. Частый случай: адрес 0 не
  реализован → **Illegal data address (0x02)**. Устройство всё равно живо.
- `no_response` — таймаут после повторов. Возможно: неверный unit id, скорость,
  чётность или отсутствие устройства.
- `transport_error` — порт не открылся, соединение отклонено, битый кадр.
  Проверьте кабель/права на порт/файрвол.

## Практика полевых работ (по результатам исследования)

Полный список источников — в [RESEARCH.ru.md](RESEARCH.ru.md). Следующие практики
рекомендуются полевыми гайдами и будут реализованы в v0.2:

- **Неизвестные настройки шины:** сначала свип baud × framing, потом адреса.
  Приоритет: 9600 8N1 → 2400 8N1 → 19200 8N1 → варианты с чётностью (8E1).
  Останов — на первом сочетании с корректным CRC.
- **Дубли адресов:** два устройства с одним адресом отвечают одновременно →
  CRC-коллизии. CRC-ошибка не должна считаться найденным устройством.
  Рекомендация: подключать устройства по одному (point-to-point) и задавать адреса.
- **Только один master:** сканирование шины при работающем PLC даёт мусор —
  отключите master или работайте в «тихом окне».
- **Исключение 02 (Illegal Data Address)** — положительный сигнал: устройство
  живо, просто опрашиваемого адреса нет.
- **Открытый порт 502 — ещё не устройство:** нужен корректный Modbus-ответ.

## Безопасность

- При обнаружении сканер отправляет только **читающие** функции (01–04).
- Функции записи (05/06/0F/10) доступны только во вкладке Manual и требуют
  явного действия пользователя. См. [SECURITY.md](SECURITY.md).
- Не ждите ответа от unit id 0; broadcast-запись из Manual может повлиять на **все**
  устройства на последовательной шине.
- На шлюзах зондирование unit id 2–247 может дойти до реальных устройств.
  Соблюдайте осторожность.

## Прогресс и события

`scan:progress` несёт `{status, total, done, found, current, errors, elapsed_ms}`.
`scan:event` — смены статуса, найденные/обновлённые устройства и финальная сводка.
Полная схема — в [API.ru.md](API.ru.md).
